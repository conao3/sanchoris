# Architecture

Sanchoris runs as a serverless control plane on AWS: Lambda functions behind API Gateway and SQS, DynamoDB for state, S3 for large objects, and EventBridge Scheduler for timers. Only Workspaces run on Fargate. This document is the contract between `crates/core`, `crates/worker`, `crates/graphql`, `crates/api`, and the CloudFormation that deploys them. `infra/tables.json` holds the table definitions as CloudFormation properties and `infra/plans.json` the plan catalog; the code reads both, so the templates and the code cannot drift.

## Runtime components

```text
Browser ── HTTPS ──> API Gateway HTTP API ──> Lambda api ───────────────┐
                       /api/* (Cognito JWT); $default: /webhooks/*,      │
                       /auth/github*, /health, the frontend (SPA)        │
workspace-agent ── WSS ─> API Gateway WebSocket API ──> Lambda channel ──┤
                       $connect: Lambda channel-authorizer (Run token)   │
                                                                         ▼
                                       DynamoDB main table (+ stream) and audit table
                                                    │ stream: kind = msg
                                                    ▼
                                             Lambda relay ──> SQS FIFO work queue ──> Lambda worker
                                                    │                 ▲                    │
                                                    └─> EventBridge ──┘ (one-time and      ├─> GitHub API
                                                        Scheduler        rate schedules)   ├─> ECS RunTask (Fargate Workspaces)
                                                                                           └─> API Gateway Management API (outbox push)
```

### Rate schedules

Each rate schedule sends the same body every time except for the scheduled time, which keeps content-based deduplication from dropping consecutive firings. The worker ignores the extra field.

```json
{"id":"00000000-0000-0000-0000-000000000000","job":{"type":"sweep_checks"},"scheduledTime":"<aws.scheduler.scheduled-time>"}
```

| Job | Rate | Does |
|---|---|---|
| `sweep_configs` | 5 minutes | `ConfigSync` for configs not synced in 5 minutes (config polling); a `push` webhook to a config's branch emits `ConfigSync` for it at once |
| `sweep_checks` | 1 minute | `CheckPoll` for check waits whose `next_poll_at` passed (check polling) |
| `sweep_task_limits` | 1 minute | `Start.Limits` (turns, cost, timeout, heartbeat) on `RUNNING`/`WAITING` tasks |
| `usage_alerts` | 15 minutes | 80% plan usage alerts (usage refresh) |
| `sweep_workspaces` | 1 minute | Records Workspaces that stopped on their own (the ECS task's `stoppedReason`, stop code, and exit code on the run and the task) and scales the egress relay to 0 when no Workspace runs |

### Jobs and messages

A job is emitted inside the `TenantTx` that causes it (`tx.emit(job)`, `tx.emit_at(job, at)`, `tx.cancel_schedule(message_id)`). Commit writes one message item per job (`pk = MSG#<uuid>`, `kind = msg`, `body` = the `Relayed` JSON, TTL 24 h) in the same `TransactWriteItems`, so state and follow-up work commit together. In AWS the stream delivers the message items to the relay (`Relay::Stream`); locally the transaction hands them to the in-memory queue and scheduler right after commit (`Relay::Direct`). Delivery is at least once; the FIFO deduplication id is the envelope id, and every handler re-reads state and ignores messages that a newer one superseded (timers compare `message_id` and are scheduled again at their `due_at` when they arrive before it, trigger schedules compare `schedule_message_id` (the config sync arms one again when its `next_run_at` is more than 10 minutes past), resumes compare `resume_at` and are scheduled again when they arrive before it or before the task's `snoozed_until`, snooze ends compare `snoozed_until`, check polls compare `next_poll_at`).

The SQS body is the `Envelope` JSON: `{"id": "<uuid>", "job": {"type": "<job>", ...}}`. Job types and their fields are `sanchoris_core::jobs::Job`.

### Local runtime

`sanchoris all` and the tests run every component in one process: the api serves HTTP and the Run channel (`/runs/channel`, the same `channel::Channel` logic as the Lambda routes over an axum WebSocket), `Store` uses `Relay::Direct` over `MemoryQueue` and `MemoryScheduler`, `LocalDriver` handles the queue and fires due schedules on the `Clock`, and DynamoDB Local (`pnpm dynamo:local`) holds the tables. `DirBlobStore` replaces S3, the local records store replaces the records bucket, and the frontend comes from `SANCHORIS_FRONTEND_DIR`. GraphQL's inline config sync and chat dispatch use the same `Worker` as `LocalDriver`.

### Client IP

The api function records the client IP of GraphQL requests (the audit events' `source_ip`) from the HTTP API's `requestContext.http.sourceIp`. When `sourceIp` is in Cloudflare's published ranges (`CLOUDFLARE_RANGES` in `crates/api/src/graphql.rs`), it takes `CF-Connecting-IP` instead; from any other address the header is ignored. The list is a copy of https://www.cloudflare.com/ips-v4 and https://www.cloudflare.com/ips-v6 (aws-infra-k8s `resources/cloudflare-ips.edn` holds the same list); when those files change, update both and run `cargo test -p sanchoris-api --lib graphql`. With `SANCHORIS_ALLOWED_SOURCES=cloudflare`, the api function answers 403 to a request whose `sourceIp` is outside these ranges, and the channel authorizer denies a `$connect` whose `requestContext.identity.sourceIp` is outside them, so a request that reaches the regional endpoint of a custom domain without Cloudflare is refused.

### Workspaces

The Fargate task gets `SANCHORIS_RUN_ID`, `SANCHORIS_BOOTSTRAP_TOKEN`, `SANCHORIS_CONTROL_URL`, `SANCHORIS_GIT_URL`, `SANCHORIS_BRANCH`, `SANCHORIS_REPOSITORIES` (comma-separated `owner/name` from the task's `start_payload.repositories`, "GitHub repositories"), `SANCHORIS_CREDENTIAL_SOURCE=channel`, and `SANCHORIS_RELAY_URL` (`http://run:<relay token>@<relay private IP>:<SANCHORIS_RELAY_PORT>`) as container overrides, and `startedBy` = the run id without dashes. CloudTrail records the overrides in the `RunTask` request and `ecs:DescribeTasks` returns them, so they carry only bootstrap credentials: the bootstrap token (the Run token's key and a distinct kind, bound to the tenant, the Run, and the Workspace, valid 15 minutes from the Workspace's `started_at`, accepted for one channel connection) and a relay token valid for the same 15 minutes. The agent's first `hello` gets `credentials` with the Run token and the Run's relay token, both valid 12 hours from `started_at`, and the agent keeps them in memory (`apps/workspace-agent/PROTOCOL.md` "Bootstrap"); an agent that loses the connection before `credentials` exits 1, and the Workspace stops. The image's entrypoint (`infra/workspace/entrypoint.sh`) removes `SANCHORIS_BOOTSTRAP_TOKEN` and `SANCHORIS_RELAY_URL` from the environment and `exec`s `tini` (which reaps orphaned processes as PID 1) with `workspace-agent` as its child and both secrets on stdin, so no process in the Workspace inherits them and no `/proc/<pid>/environ` holds them. The task definition therefore leaves `initProcessEnabled` off: ECS's init process would keep the original environment as PID 1. The relay URL carries a relay token as its password: hex-encoded JSON `{"run", "exp", "allow"}` (the Session's `Network.Allow`) and its HMAC-SHA256 under `RELAY_TOKEN_SIGNING_KEY`. The relay verifies the token on every `CONNECT`, so the allow list travels with the Run and the relay needs no database. The image (`infra/workspace/Dockerfile`, built for `linux/arm64` and `linux/amd64`) sets `SANCHORIS_SOCKET_PATH`, `SANCHORIS_WORKSPACE_DIR`, `CLAUDE_CONFIG_DIR`, `SANCHORIS_CLAUDE_PATH` (the Claude Code binary bundled with the Agent SDK), `NODE_USE_ENV_PROXY=1`, `HTTPS_PROXY` and `HTTP_PROXY` = `http://127.0.0.1:3129` (the agent's forwarder, which adds the relay token to each `CONNECT` it passes to the relay), `NO_PROXY=127.0.0.1,localhost`, and the git credential helper `sanchoris git-credential`, and runs `workspace-agent` as `node` (uid 1000). The root file system is read-only (the task definition's `readonlyRootFilesystem`); the container writes only to three bind mounts on the task's ephemeral storage (30 GiB): `/workspace` (the clones and the session's edits), `/home/node` (`CLAUDE_CONFIG_DIR` = `~/.claude` with the session records, `~/.local`, the npm and pnpm caches and store, `~/.gitconfig`), and `/tmp` (the agent socket `SANCHORIS_SOCKET_PATH`, Claude Code's `claude-<uid>` and `cc-socks`, the Node compile cache). The image declares the three as `VOLUME`, so Fargate fills each one from the image with its content, owner, and mode (`node` for `/workspace` and `/home/node`, 1777 for `/tmp`) before the container starts; `docker run --read-only` with the image gives the same layout locally.

With `SANCHORIS_CREDENTIAL_SOURCE=channel` the agent asks the channel for the worker credential before it starts the session (`worker_credential_request`: the channel decrypts the Session's `Worker.Credential` and returns `ANTHROPIC_API_KEY`, or `CLAUDE_CODE_OAUTH_TOKEN` for a key that starts with `sk-ant-oat`). The agent keeps the credential in memory and runs a credential proxy on `127.0.0.1`: Claude Code gets `ANTHROPIC_BASE_URL` pointing at it and a placeholder in the same variable, and the proxy replaces the placeholder with the credential on each request to `https://api.anthropic.com` (`Authorization: Bearer` with the `oauth-2025-04-20` beta for an OAuth token, `x-api-key` for an API key). Claude Code (2.1.311, bundled with the Agent SDK) sends every model request to `ANTHROPIC_BASE_URL` with either kind of credential and, with `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1`, contacts no other host. So none of the provider credential, the bootstrap token, the Run token, and the relay token is in the environment of Claude Code, its tools, or `exec` commands, and a session that copies its environment or files somewhere it can write (a commit, an allowed host) does not leak them. What stays: any process in the Workspace can send provider requests through the credential proxy for the life of the Workspace (it cannot read the credential), and the agent runs as the same user (`node`) as the session, so a process that reads another process's memory (`ptrace`, `/proc/<pid>/mem`, where the kernel allows it for the same user) can read the credentials from the agent. The agent clones the repositories itself and gets GitHub tokens for `git` through `git_token_request`: a GitHub App installation token narrowed with `repository_ids` (the ids of the names in the Session's `GitHub.Repos`, from the config's map; the whole installation when a pattern is `owner/*`) and `permissions` (`GitHub.Permissions`), valid for one hour. The token therefore sits in the Workspace for the life of a `git` command and in the agent's memory until it expires; the relay does not intercept TLS. Keeping the token outside the Workspace (the relay adding it to GitHub requests) needs TLS interception with a CA that the image trusts and is not built. The relay image (`infra/relay/Dockerfile`) runs `apps/egress-relay` (`SANCHORIS_RELAY_PORT`, `RELAY_TOKEN_SIGNING_KEY`, `SANCHORIS_RELAY_PLATFORM_HOSTS`, `SANCHORIS_RELAY_DENY_HOSTS`) and logs one JSON line per `CONNECT` with the run, the host, and the decision. Both Dockerfiles pin their `node:26` base image by digest; to move to a newer one, read the index digest with `docker buildx imagetools inspect node:26-bookworm` (`node:26-alpine` for the relay) and replace it.

The egress relay runs only while Workspaces need it. Before `RunTask`, `EcsRunner` takes the relay lease (the `RELAY` item: a conditional update sets `lock_owner` and `lock_until` = now + 60 s when no live lock exists), sets the relay service's desired count to 1, adds the run to `holders`, and releases the lock; then it waits up to 240 s for a relay task whose desired and last status are `RUNNING` and reads its private IP from the task's ENI. A failed `RunTask` gives the run back. `stop_workspace` (finished or idle runs) and the `sweep_workspaces` job (while the desired count is above 0) take the lock, drop the stopping run, keep the holders whose Workspace task is still listed (`ListTasks` of the Workspace family, desired status `RUNNING`, matched by `startedBy`) or that asked within the last 10 minutes, and set the desired count to 0 when no holder and no Workspace task remains. Concurrent workers serialize on the lock, so one never scales the relay down while another is starting a Workspace on it. A relay task that ECS replaces gets a new IP; Workspaces that already run keep the old address (their `relayUrl` is fixed at `RunTask`) and lose their way out when the old task stops. The relay service deploys with `MinimumHealthyPercent` 100 and `MaximumPercent` 200, so a deployment starts the new relay task before it stops the old one, which keeps the old address working while the new task starts but not after; deploy a new relay image or task definition when no Workspace runs (`ListTasks` of the Workspace family is empty).

The Session's `Workspace.Architecture` picks the task definition: `arm64` the ARM64 family, `x86_64` the X86_64 family. The tenant's Plan picks the size: `start_workspace` copies the Plan's `workspace_cpu` and `workspace_memory_mib` (`infra/plans.json`: Free and Starter 1024 and 4096, Pro, Max, and Admin 2048 and 4096) to the Workspace item, and `RunTask` passes them as the task-level `cpu` and `memory` overrides, so one task definition per architecture serves every Plan and a new size is a change to the plan catalog only. Both run the same image, pushed per architecture as `<tag>-arm64` and `<tag>-amd64`: the Dockerfile runs every `RUN` step on the build platform and installs the target's npm packages (pnpm `supportedArchitectures`, so the Agent SDK brings the `linux-arm64` or `linux-x64` Claude Code binary) and `tini` (`apt-get download tini:<arch>`), so a build for the other architecture needs no emulation.

`RunTask` asks for the capacity provider `FARGATE_SPOT` (weight 1, no `launchType`). Fargate does not move a Spot request to On-Demand by itself, so when the response's `failures[].reason` says the capacity is missing (`Capacity is unavailable at this time...` or a `RESOURCE:` reason), the worker logs the reason and calls `RunTask` again with `FARGATE`; other failures and exceptions fail the start. The Workspace's `capacity_provider` records the provider that started it, and the run screen shows it (`Workspace.capacityProvider`).

A Workspace is recorded before it is launched. `start_workspace` commits the `WS#` item without `platform_ref`, the `start` outbox item, and the run in `creating`, then calls `RunTask` and writes the task ARN as `platform_ref` and the capacity provider in a second transaction. Each `RunTask` gets `clientToken` = `spot-` or `ondemand-` and the Workspace id without dashes, so the Spot attempt and the On-Demand attempt are two requests (ECS answers a repeated token with the first response, which for a Spot failure is that failure), the tags `sanchoris:tenant`, `sanchoris:task`, `sanchoris:run`, and `sanchoris:workspace`, and tokens that expire 12 hours after the Workspace's `started_at`, so a retry for the same Workspace (a worker that crashed or timed out after `RunTask`, an optimistic-conflict retry) gets the task the first call started; a retry whose parameters differ (a new relay address) gets `ConflictException`, whose `resourceIds` name that task. `reconcile` launches an open Workspace without `platform_ref` again. `sweep_workspaces` closes a Workspace that still has no `platform_ref` 15 minutes after `started_at` (the run's `error` and the task's `cause` say it did not launch) and stops every running task of the Workspace families whose tags name no open `WS#` item with that ARN, which covers a launch the client token no longer deduplicates (24 hours). The worker Lambda gives each invocation a deadline 30 s before Lambda's, and the relay lock wait (90 s) and the relay start wait (240 s) end at it. A run whose Workspace stopped before its first turn (no `record_s3_key`, `turns` = 0) gets the Task's instruction again in its next `start`.

A Workspace interrupted by the platform is restored, not stopped. ECS sends `SIGTERM` two minutes before a Spot interruption; the agent sends `stopping`, interrupts the running turn, uploads its record, and exits 0 (`apps/workspace-agent/PROTOCOL.md`, "Stopping on SIGTERM"), and the worker writes `signaled_at` on the open Workspace of the run. When `sweep_workspaces` finds the task stopped, it counts the Workspace as interrupted if `signaled_at` is set or the stop code is `SpotInterruption` or `TerminationNotice`: it closes the Workspace at the interruption (the earlier of `signaled_at` and the task's `stoppingAt`), so the Workspace seconds of the Tenant stop there, sets the run to `idle` without an `error`, marks the `exec` items whose invocation still waits and the `user_message` items delivered after the interruption as undelivered, and, for a `RUNNING` task, sends the restore notice as a `user_message`. That message wakes `reconcile`, which starts a new Workspace with `resume` from the run's latest record on the Task branch, like the restore after an idle stop; for a waiting task the next message or a redelivered `exec` starts it. An interrupted turn's `turn_end` (`result: "interrupted"`) records usage and does not decide the task.

Workspace containers have no log driver. `workspace-agent` sends its log lines over the Run channel (`log` events become `LOG#` items). A Workspace that stops before the channel connects (image pull failure, a crash at start) is found by `sweep_workspaces`: `DescribeTasks` shows the task `STOPPED`, and the worker closes the Workspace, sets the run to `idle` with `error` = the `stoppedReason`, stop code, and the container's exit code or reason, and moves a `RUNNING` task to `NEEDS_YOU` with `Workspace.Stopped` and the same text as `cause`.

The network of Workspaces is the stack's choice (aws-infra-k8s `WorkspaceNetwork`). In the strict network they run in a subnet without an internet route, pull images through ECR interface endpoints and the S3 gateway endpoint, and the relay is their only way out. In the public network they run in the public subnet with a public IP, pull from ECR over the internet, and their security group allows port 443 to the internet besides port 3128 to the relay: `HTTPS_PROXY` makes Claude Code, git, and `NODE_USE_ENV_PROXY` clients use the relay, but a process that ignores the proxy reaches any host on port 443, so the relay's lists are advisory for a misbehaving agent.

Tenant isolation is enforced in the application: every function uses one role, and `TenantTx` rejects keys outside its tenant. No request assumes a tenant-scoped role.

## GitHub repositories

A repository is identified by its GitHub repository id; `owner/name` is a display cache that follows renames and transfers. This is the model of Vercel (`link.repoId`), Netlify (`repo_id`), and Renovate (the repository list comes from the App installation).

- **Installation list.** Each GitHub integration keeps `details.repositories`, a list of `{id, full_name}`: written from `GET /installation/repositories` when the installation is connected and kept by the `installation`, `installation_repositories`, and `repository` webhooks. The GitHub App subscribes to `repository` besides the events of the triggers.
- **Config.** `repository_id` is the key and `repository` the current name; the guard is `CONFIGREPO#<repository id>#<root>`. `addConfig` resolves the entered name to an id before it stores the config. A sync reads through the connected installation whose list holds the id, calls `GET /repositories/{id}` (and writes the current name), and reads the branch head, the tree, and the blobs under `/repositories/{id}/`.
- **Names in `sanchoris.yaml`.** The exact names of a revision (`Projects.<p>.Repos.<r>.Repo`, `Sessions.<s>.Repos`, `Sessions.<s>.GitHub.Repos` without `*`, and the strings of a GitHub trigger's `detail.repository` after project keys become names) resolve at activation: a name in an installation list, otherwise `GET /repos/{owner}/{name}` with that installation's token (GitHub redirects a renamed repository's old name) when the returned id is in the installation list. The result is the config's `repositories` map (the name as written → `{id, full_name}`), and every project `repository` item carries `github_repository_id` and `full_name`. A name that does not resolve fails the sync and leaves the previous revision active.
- **Matching events.** Normalized GitHub events carry `detail.repository_id`. Before a trigger's EventPattern is evaluated, `detail.repository` is replaced, for the trigger's config, with the name in the config's map whose id is the event's id; when the event's name is in the map under another id, with `#<id>`, so that no name condition of that config matches a different repository that took the name; otherwise it stays the event's name. The InputTransformer and the skills see the event's current name.
- **Workspaces.** `SANCHORIS_REPOSITORIES` holds the current names: the project's `repository` items, or the names of `Sessions.<s>.Repos` looked up in the config's map. `git_token_request` narrows the installation token with `repository_ids` from the map; a pattern `owner/*` leaves the whole installation.
- **Tasks.** A task started by a GitHub event is named by the repository id: `github:<repository id>#<issue number>` for issues and pull requests, `github:<repository id>@<head sha>#<check run id>` for check runs (`items::github_task_name`); its channel carries `repository` (the name at the event) and `repository_id`. The task name guard (`TASK#<name>`) and the `T#<t>#TASKNAME#<name>` index use that name, so the parent and blockers of a sub-issue (`GitHubReader::issue_relations` asks GitHub for `repository { nameWithOwner databaseId }`) are found after a rename. Screens and messages show `Task::display_name`: the current name from the installation lists, the event's name when the repository left them. `IssueRef.repository` and `Output.repository` show the current name the same way.
- **Check waits and outputs.** A check wait's `CHECKWAIT#` marker keeps the ids of its repositories next to their names (resolved from the installation lists when the wait starts; a name outside them fails the step with `Resource.InvalidParameters`), and a `check_run` webhook nudges the waits whose ids hold the event's `repository_id`. An output (`SR#<n>#OUT#<kind>#<repository id>#<number>`) carries `repository_id`, resolved from the resource's `Repo` or the repository of its GitHub URL.
- **Renames and transfers.** `repository.renamed` and `repository.transferred` update the installation list, the `repository` of every config with that id (audit `config.rename`), the config maps, and the `full_name` of the project `repository` items.
- **Removal.** `repository.deleted` and `installation_repositories.removed` disable the configs whose `repository_id` is the repository's id. `installation_repositories.added` only extends the installation list; a config is added with `addConfig`. No mutation removes a config: the user removes the repository from the App installation on GitHub.
- **Disabled configs.** Disabling sets `status` to `disabled` and `sync_error` to the reason, empties the map, deletes the guard (so the repository can be added again as a new config), and audits `config.disable`. The config's definitions go the way of definitions a revision drops: triggers get `removed_at` and their schedules are cancelled, and the `project`, `repository`, `session`, and `skill` items are deleted. Its tasks that are not finished are aborted like `stopTask`, with the reason, because the repository they work on is gone from the installation. The config item, its revisions, its trigger items, and the finished tasks stay for the history. A disabled config has no `gsi2` key, so the sweep skips it, and `syncConfig` refuses it.
- **Sync errors.** `config_sync::sync_config` writes a GitHub error or a name that does not resolve to the config's `sync_error` and finishes the job, so a failing config never reaches the DLQ; the 5-minute sweep tries again, and a successful sync clears it. `Config.syncError` shows it, or the reason a config is disabled.
- **Backfill.** `sanchoris-backfill-stable-keys` (`crates/api`) moves data written in an earlier layout. For each tenant it activates the active revision of each config again and deletes the definition items outside `DEF#` ("Config activation"), renames GitHub tasks to the repository-id name (the id from the task's trigger event; the `TASK#` guard moves with the task), adds `repository_ids` to check wait markers (a marker whose names are outside the installation lists is deleted; polling continues), and re-keys outputs by `repository_id` (from the installation lists, or the task's repository when the output is on it; an output whose repository resolves neither way is deleted). Items already in the current layout are left alone, so it can run again and prints nothing then. An administrator runs it right after deploying the code, with the store variables, `GITHUB_API_URL`, and `SANCHORIS_SECRETS_PATH` (it reads `github-app-id` and `github-app-private-key`):

```bash
SANCHORIS_TABLE_MAIN=<prefix>-sanchoris-main SANCHORIS_TABLE_AUDIT=<prefix>-sanchoris-audit \
  SANCHORIS_DOCS_BUCKET=<docs bucket> SANCHORIS_SECRETS_PATH=/<prefix>/sanchoris/ \
  GITHUB_API_URL=https://api.github.com \
  nix develop -c cargo run -q -p sanchoris-api --bin sanchoris-backfill-stable-keys
```

### Config activation

Readers see one revision of a config at a time. The config item's `active_revision_id` names it, and the definitions are keyed or marked by revision:

- **Projects, repositories, sessions, skills** live at `DEF#<revision id>#PROJECT#<name>`, `DEF#<revision id>#PROJECT#<name>#REPO#<repo>`, `DEF#<revision id>#SESSION#<name>`, and `DEF#<revision id>#SKILL#<name>` (`keys::*_prefix`). Every reader takes the revision first: dispatch from the matched trigger (`config_revision_id`), which also resolves the Session's checkout to `owner/name` into the task's `start_payload.repositories` that every Workspace of the task clones, and the screens from the config's `active_revision_id`.
- **Triggers** keep one item per name (`TRIGGER#<name>`, with the id, the schedule, and the trigger events), because their state outlives revisions. An activation writes the next definition into the item's `next` (`{config_revision_id, definition}`, `definition` null for a trigger the revision drops); `Trigger::in_revision(active)` gives the definition of the active revision: `next` when it names the active revision, otherwise the item's own fields when they belong to it and the trigger is not removed.

An activation of revision R has three steps. **Stage**: write R's projects, repositories (keeping the previous revision's `prebuild_status`), sessions, and skills under `DEF#<R>#`, set `next` on every trigger, and insert new triggers with R as their revision, in batches of at most 90 writes; none of it is visible while another revision is active. **Switch**: one conditional `Put` of the config with `active_revision_id` = R and the `repositories` map, with the `config.activate` audit event. **Settle**: fold each trigger's `next` into its fields (or set `removed_at`), arm and cancel schedules, and delete the `DEF#` items of other revisions, again in batches. A sync whose head is already the active revision runs settle again, so a stage or a settle that stopped between batches finishes on the next sync. Dispatch checks the version of every config it read (`TenantTx::assert_unchanged`), so an event evaluated across a switch is evaluated again.

## Plans

A tenant has one plan, `plan_id` on the tenant item, and the plan holds its limits (`infra/plans.json`). `task_limit`, `workspace_seconds_limit`, and `member_limit` are a number or `null` for no limit; the plan catalog and the `plan` items state each of them explicitly, and a plan item without one of these attributes does not decode. A tenant whose `plan_id` names no plan item dispatches no task (`DbError::Missing`), so a wrong name never runs without limits.

| Plan | Price | Tasks | Workspace hours | Period | Members | Live workspaces | Inbound events per minute | Workspace | Computes |
|---|---|---|---|---|---|---|---|---|---|
| Free | 0 | 5 | 10 | total | 1 | 1 | 20 | 1 vCPU, 4 GiB | standard |
| Starter | USD 20 | 10 | 50 | month | 3 | 2 | 60 | 1 vCPU, 4 GiB | standard |
| Pro | USD 100 | 50 | 250 | month | 10 | 5 | 120 | 2 vCPU, 4 GiB | standard |
| Max | USD 200 | 200 | 500 | month | 30 | 10 | 300 | 2 vCPU, 4 GiB | standard |
| Admin | none | no limit | no limit | total | no limit | 10 | 300 | 2 vCPU, 4 GiB | standard |

The per-task limits (turns, cost, timeout, idle time, children) and the retention of Admin are those of Max.

**Admin.** Admin is the plan of the tenants that Sancode members create, the rule sanrecap applies to its users:

- **Who.** A sign-in is privileged when its Cognito ID token has `email_verified` true (a boolean or the string `"true"`) and an `email` whose domain is `billing::PRIVILEGED_EMAIL_DOMAIN` (`sancode.dev`, compared without case). `provision` computes it on every request from the token (`CurrentUser.privileged`, `AuthUser.privileged`); it is not stored. An access token has no email and is not privileged.
- **Creation.** `Viewer.newTenantPlans` is `[Admin]` for a privileged sign-in and the plans of `Query.plans` otherwise. `createTenant` of a privileged sign-in takes only `admin` (`BAD_USER_INPUT` for another plan), and `admin` from anyone else is `FORBIDDEN`. The tenant is created active with no Checkout, no Stripe customer, and no `UNIQ#free_tenant` guard, so a Sancode member can create any number of them.
- **Existing tenants.** The plan is decided once, from the sign-in of the creator at creation. A tenant created on another plan keeps it, whatever the email of its owner; signing in later converts nothing.
- **Members.** Membership does not change a plan: a Sancode member who joins a tenant on Free or a paid plan leaves that plan as it is, and a tenant on Admin stays on Admin whoever joins or leaves.
- **Billing.** `Query.plans` (the plans for sale) leaves Admin out, and Admin has no Stripe price. `changePlan` refuses a tenant on Admin (`CONFLICT`) and Admin as the target (`FORBIDDEN`); `openBillingPortal` refuses a tenant on Admin (`CONFLICT`). Every Stripe event that reaches a tenant on Admin (`checkout.session.completed`, `customer.subscription.updated` and `deleted`, `invoice.paid`, `invoice.payment_failed`) is recorded as `ignored` with the reason "tenant <t> is on the admin plan" and changes nothing. `Plan.isAdmin` tells the Billing screen to show the plan without the plan table, the Change buttons, and "Manage in Stripe".
- **Limits.** Dispatch counts tasks and workspace seconds as on any plan but stops only at the concurrency of 10 live workspaces; usage alerts skip the metrics without a limit, and invitations have no seat limit. The receive limit is 300 inbound events per minute, as on Max.

**Receive limit.** Each tenant accepts at most the plan's `inbound_events_per_minute` inbound events per clock minute (UTC), so that a flood from one tenant cannot take the worker's shared concurrency or run up cost for the others. Every plan, Admin included, has a number; the attribute is required in the catalog and the plan items.

- **What counts.** GitHub deliveries that become inbound events (`issues.labeled`, `issue_comment.created`, `check_run.completed`, source `github`, counted after the duplicate check so a redelivery of a recorded event answers `duplicate` and counts nothing), `sendChatMessage` (source `web`), and human replies that wake an agent: `resumeTask` (source `reply`). Webhooks that only keep state (`installation`, `installation_repositories`, `repository`, and `push`, which queues config syncs) never count and are never refused, and neither are approvals (`POST /api/approvals`, one resolution per approval wait), schedules, config syncs, snoozes, and stops.
- **Check.** `receive::admit_inbound` runs before anything is recorded or dispatched: Get the tenant and its plan, then one `UpdateItem` on `T#<t>#RECEIVE` `RATE#<minute>` that adds 1 to `received` under the condition `received < limit` (`Store::increment`). The item sits in its own partition per tenant, away from the tenant item that every status change touches, and needs no read or transaction, so concurrent requests never exceed the limit and never conflict.
- **Over the limit.** The event is dropped and nothing else is written for it: a second `UpdateItem` adds 1 to `dropped`, and the first drop of the minute writes the audit event `tenant.receive_limit` (actor `system`, the source as `actor_ref`, metadata `source`, `key`, `limit`, `window_start`). The GitHub webhook answers `429` with `Retry-After` (seconds to the next minute) and `{"status": "dropped", "reason", "limit", "retryAfterSeconds"}`; GitHub does not redeliver on its own, and the non-2xx status marks the delivery failed in the App's recent deliveries, where an operator can redeliver it. The GraphQL mutations fail with the code `RATE_LIMITED` and the extensions `limit` and `retryAfterSeconds`. The reason reads `receive limit: the tenant already received <limit> events in the minute from <window start>; retry after <n> s`.
- **Per trigger.** The per-trigger start limit (`Settings::trigger_starts_per_hour`, `RATE#<hour>` in the trigger partition) still applies to the events that the tenant accepted.

## Data model

### Tables

| Table | Keys | Indexes | Other settings |
|---|---|---|---|
| `main` | `pk` (S), `sk` (S) | `gsi1` (`gsi1pk`, `gsi1sk`, ALL), `gsi2` (`gsi2pk`, `gsi2sk`, ALL) | TTL `expires_at`, stream `NEW_IMAGE`, PITR, deletion protection, on-demand |
| `audit` | `pk` = `T#<tenant>`, `sk` = `<at>#<id>` | — | TTL `expires_at` (the plan's `audit_retention_days`), PITR, deletion protection; IAM denies `UpdateItem`, `DeleteItem`, `BatchWriteItem`, PartiQL updates and deletes, `DeleteTable`, and `UpdateTimeToLive` (`appendOnlyDeniedActions`) |

Every item in `main` has `kind` (the entity), `v` (a version incremented by every write), and its own attributes. Times are strings `YYYY-MM-DDTHH:MM:SS.ffffffZ` (UTC, microseconds), which sort by time; numbers in keys are zero-padded to 12 digits. JSON values are stored as JSON strings. A string attribute longer than 32 KiB is stored in the `docs` bucket at `docs/<tenant>/<sha256>` and replaced by `{"$blob": "<key>"}`; reads restore it. Message items (`MSG#`) are written inline: a `Relayed` body carries ids, times, and schedule names, well under 1 KiB, so the relay reads it from the stream image and needs no access to the `docs` bucket. No other attribute may make an item exceed 400 KB.

### Transactions

`TenantTx` is the unit of work. `get` and `query` read with strong consistency, remember each item's version, and return the transaction's own staged writes; `insert` writes with `attribute_not_exists(pk)`, `put` replaces with `v = <read version>`, `delete` checks the read version (an item deleted without a read must exist: `attribute_exists(pk)`), and `update` applies an update expression (counters with `ADD`, conditions with `cap_after` and `require`). An `update` of an item staged for `insert` or `put` folds into the staged item and rejects `cap_after` and `require` with `DbError::ConditionOnStagedPut`. `commit` sends everything, including message items and audit inserts, in one `TransactWriteItems` (at most 100 items, otherwise `DbError::TooManyWrites`). A failed condition or a concurrent transaction returns `DbError::Conflict`; callers re-run the whole operation (`store::retry`, `Worker::handle`, the GraphQL mutations). `list` reads a `Listing` (a partition or index key, a sort key range such as a prefix or a lower bound, ascending or descending, an optional limit) and keeps the items of one entity that pass a filter in code, paging until the limit is reached; it does not track versions. `TenantTx::list` rejects partitions outside the tenant like `get`. Indexes (`gsi1`, `gsi2`) are eventually consistent and are only used for listings and sweeps, never for decisions inside a transaction. `Store::increment` writes one counter outside any transaction with a single `UpdateItem`: it adds 1 to the counter and `v`, sets the item's other attributes with `if_not_exists`, and, given a bound, requires the counter to be absent or below it, returning `None` when it is not; the receive limit uses it so that concurrent requests are counted without conflicts.

### How the Postgres guarantees carry over

| Guarantee | Postgres | DynamoDB |
|---|---|---|
| Tenant isolation | Row-level security on `tenant_id` | Every tenant key starts with `T#<t>`. `TenantTx` rejects any key outside its tenant (`DbError::CrossTenant`) except the global prefixes `UNIQ#`, `USER#`, `INVITEMAIL#`, `MSG#`, and rejects writes to `PLANS`. Every function runs under one role; isolation is the application check |
| Atomic engine steps | One SQL transaction per step | `persist_step` stages the skill run, entries, invocations, timers, notifications, and task decisions in one `TenantTx`; the step commits with one `TransactWriteItems`. A step makes at most `MAX_TRANSITIONS_PER_STEP` (70) state transitions, one `state_entry` write each, which leaves 30 items for the rest of the step; the next transition fails the skill run with `States.Runtime`. Config validation bounds every time value of a skill (`TimeoutSeconds`, `Seconds`, `IntervalSeconds`, `MaxDelaySeconds`) by the plan's `maxTaskTimeoutSeconds` and `BackoffRate` to 1–10, and the engine computes times with checked arithmetic, failing the skill run with `States.Runtime` when one overflows |
| Uniqueness and idempotency | `UNIQUE` constraints, `ON CONFLICT DO NOTHING` | Natural keys (`EVT#<key>`, `TASK#<name>`, `SR#<n>#E#<seq>`, `OUT#…`, `ALERT#…`) or guard items, written with `attribute_not_exists`; a losing writer gets `Conflict`, retries, and reads the winner (`Recorded::Duplicate`) |
| Concurrency cap | `FOR NO KEY UPDATE` of the tenant, `count(*)` of `RUNNING` | `live_workspaces` counter on the tenant item: a run holds a slot (`holds_slot`) from its dispatch until its workspace is gone, also while its task is `WAITING` or `NEEDS_YOU` with the workspace alive until `IdleSeconds`. Dispatch takes one slot per run it creates or restarts, with the conditions `live_workspaces <= max_concurrency − delta`, `tasks_this_period <= task_limit − delta` (counting only tasks that start for the first time), and `status = active`. Reconcile takes a slot the same way before it starts a workspace for a run that holds none (a message to a run whose workspace stopped, a restore after an interruption); without a free slot the task goes back to `PENDING` with a new `PENDINGTASK#` marker, keeping its `WAITING` reason, and dispatch later restarts the same run. Closing a workspace (idle stop, a finished run, an exit the sweep observes) and a reconcile of a run that holds a slot but needs no workspace give the slot back in the same transaction and queue `Dispatch` |
| Queue claiming | `FOR UPDATE SKIP LOCKED` | SQS FIFO hands each message group to one consumer at a time; handlers re-read state, act only on `pending`/`waiting` items, and commit with version conditions, so a redelivered or concurrent message changes nothing twice |
| Outbox ordering | `GENERATED ALWAYS AS IDENTITY` | `next_outbox_seq` on the run's `#CHANNEL` item, read and incremented in the enqueuing transaction |
| Append-only audit | `REVOKE UPDATE, DELETE`, trigger | Separate audit table with the IAM deny above; the app only inserts with `attribute_not_exists` and `TenantTx` refuses `put`, `update`, and `delete` on it (`DbError::AppendOnly`) |
| Large values | `jsonb`, `text` | Offloaded to the `docs` bucket over 32 KiB, key in the item |
| Retention | Periodic deletes | TTL on audit events, usage snapshots, run log entries, and message items |
| Timers | `due_jobs` polled | EventBridge one-time schedules carrying the job; `engine_timer` items and `next_run_at` make cancellation and re-arming checkable |

## Open decisions

- Retention of task data: TTL covers audit, snapshots, logs, and messages. Deleting a finished task's partitions after the plan's `retention_days` needs a scheduled `purge` job; the offloaded `docs/` objects then need a lifecycle rule or reference tracking.
- Audit tamper resistance stops at IAM: an app role with `PutItem` could overwrite an existing event by key. S3 Object Lock on the `t/<t>/audit/` objects of the records bucket would make exported history immutable.
- Hot partitions: `T#<t>` holds the tenant counters that every status change touches; at high volume the counter moves to its own sharded items. The sweep partitions in `gsi2` are single keys and may need shards.
